# Delegation: Dispatch and Receive

Use this procedure after choosing a suitable assignment. See [the operating model](operating-model.md) for roles, decision rights, and why to choose persistent workstreams or bounded subagents. See [controller practice](controller-practice.md) for batch selection, integration capacity, context lifetime, and whole-project cost. Delegation transfers work, not the parent's accountability or new authority.

## 1. Establish a dispatchable result

State the independent return artifact, how it will be checked, and its shared dependencies in one sentence. If these are unclear, perform a bounded investigation or keep the work with one owner first. Confirm that someone can receive and integrate the result before admitting it to the next batch.

Check the actual tools and authorization. Separate user chats, internal subagents, background automations, and external messages are different capabilities. Consent to collaborate does not authorize arbitrary chat creation, contact, spending, or permission changes. Reuse a suitable existing owner where possible. Without an authorized delegation mechanism, do the work within the current agent; do not describe a written plan as a completed dispatch.

## 2. Send a bounded brief with original evidence

Take only the relevant fields from [Templates](templates.md). Include:

- The result and every mandatory condition within this assignment, linked to the current authoritative requirement and its revision.
- The baseline or input version, established facts, important uncertainty, and original evidence the owner must inspect. Preserve contrary evidence and ambiguities rather than supplying only the expected conclusion.
- Permitted read/write paths and resources, exclusions, protected data, and the actual shared-resource owner.
- Inputs, outputs, consumers, shared contracts, and dependencies that must be settled before writing.
- Required checks, relevant real samples, and the evidence level needed for the return.
- Local autonomy, explicit user confirmation points, stop or escalation conditions, and whether further delegation is permitted.
- The artifact location, receiving owner, reporting checkpoint, and any budget or time window actually set by the user or project.

Give the minimum sufficient context, not the entire conversation by default. A pointer must identify material the owner can actually access; a short summary does not replace required original reading. A simple stop or park instruction needs only its scope, action, and acknowledgment, not a full delivery brief.

## 3. Acknowledge the baseline and execute

The recipient verifies the baseline, scope, relevant evidence, and write ownership, then acknowledges receipt. Report incompatible assumptions before substantial work. This is operational confirmation, not another request for user permission to perform already authorized work.

Treat shared files, interfaces, databases, ports, services, and cloud environments as actual shared resources. Separate worktrees do not isolate all of them. Use one writer for a shared resource, or one integrator applying identifiable contributions. Follow [Ownership and review](ownership-review.md) before changing writers; a status note does not prevent concurrent writes. Preserve unrelated changes.

Within the brief, choose local methods, implement, and self-check the complete assigned result. Independent reads may run in parallel; sequence dependent actions, approvals, and writes to shared resources. Do not expand the scope merely to make the local solution more convenient.

## 4. Keep authority and child work bounded

Coordinate shared-contract changes with the responsible parent and affected owners before they propagate, using facts from the same version. Escalate changes to acceptance, protected resources, or external effects that fall outside the brief before taking affected actions. The lead handles cross-stream decisions within authority; only genuine authorization gaps, consequential ambiguity, or explicit user gates go to the user. Do not make the user relay decisions between chats or repeatedly approve routine continuation.

A subagent may delegate again only when all conditions hold: platform and user permission, allowance in the parent brief, divisible scope, remaining concurrency and any applicable budget, and a parent able to review the returns. Reassess with the lead before adding an organizational layer. Do not create unbounded trees, repeated mutual wakeups, or loops that return the same task for redispatch.

The parent checks and consolidates child output before reporting upward. A bounded subagent does not acquire a global roadmap, release authority, or ownership of the main project record by receiving an assignment. A reviewer remains read-only for the candidate; fixes belong to the author or authorized integration writer. Call a review independent only when a separate evaluator has not been steered toward the expected conclusion. Shared agreement still requires real evidence.

## 5. Monitor meaningful events at low cost

Report at the agreed event: a runnable slice, a resolved question, new evidence, a blocker, or a boundary change. Routine progress within scope can continue; escalate material risk or conflicting assumptions promptly. Major and exception checkpoints follow [controller practice](controller-practice.md).

Prefer compact status and evidence references, including the current version and next action. Expand original logs for a decision, conflict, or integration risk, not on every poll. Use available waits or batched snapshots rather than repeatedly asking whether a long-running command is finished. With no new evidence, check less often; do not restart or duplicate the task to obtain progress.

Only create or continue background monitoring when authorized and supported. A timer firing proves neither task completion nor release of a write lock. User updates still follow [Reporting](reporting.md), including requested complete tables and notification timing; an internal compact return does not waive those requirements.

## 6. Return a candidate that can be inspected

Before returning, self-check the assigned outcome and identify what was not verified. Return the requirement and brief revision, exact candidate version or diff, artifact location, changed behavior, evidence with its environment and time, limitations or contrary evidence, affected shared resources, and the proposed next action. State any operation still in progress or with an unknown outcome, and whether writing has actually stopped. Do not dump full terminal histories when precise evidence references suffice.

The receiver confirms the return belongs to the effective brief and correct baseline. A return can be **received, awaiting review, or awaiting integration** without being delivered. Inspect original evidence where needed; do not merely copy the assignee's completion label. Specify a missing item or finding and return that bounded correction rather than restarting the entire assignment.

Integrate under the assigned writer and verify the real combination at one candidate version. If requirements or code changed, reuse only evidence whose relevant conditions still apply. Project delivery follows the full acceptance and environment boundary, not the count of completed child tasks. The parent retains that judgment.

## 7. Close, revise, or park the assignment

Once the result is integrated or the bounded investigation is received and evaluated, close the temporary assignment. Reopen it only for a specific authorized correction or follow-up. Do not keep a subagent busy with an unrelated roadmap because it remains available.

When the brief changes, update the affected revision, evidence validity, and owner before conflicting work continues. When paused or blocked, preserve the candidate, ownership, unknown operations, and next safe step; independent authorized work may continue. Confirm a safe stop before transferring writes. Use [Recovery](recovery.md) for pauses, uncertain outcomes, and handoffs rather than inferring that an interrupted tool or silent owner has stopped.
